SUGGESTION ID: PL-001 + PL-002
TITLE: LAN-IP cookie rejection + fresh-account dashboard crash

WHAT WAS FOUND: (1) Production builds marked the session cookie Secure;
  browsers silently reject Secure cookies over plain HTTP on
  non-localhost hosts — user on http://192.168.56.1:3000 was bounced to
  /login the moment onboarding finished (cookie trace: 0 cookies
  stored). (2) The fix exposed a second crash: fresh accounts with no
  topics have no plan blocks, and relativeDay("") threw
  RangeError: Invalid time value on the dashboard.
WHAT WAS CHANGED: (1) Session cookie Secure flag now derived from the
  real request protocol (x-forwarded-proto aware) — session.ts; same
  for the OAuth state cookie, plus request-origin fallback for the
  OAuth redirect base — auth/google/route.ts. (2) Dashboard renders
  relativeDay only when data.today exists; Today page falls back to
  todayISO() — app/page.tsx, today/page.tsx.
FILES/MODULES AFFECTED: src/lib/auth/session.ts,
  src/app/auth/google/route.ts, src/app/app/page.tsx,
  src/app/app/today/page.tsx, README (troubleshooting).
WHY THE CHANGE WAS MADE: user-reported blocker ("after login I am not

VERIFICATION RESULT: green.

ENTRY #10
DATE: 2026-09-06
SUGGESTION ID: PL-013
TITLE: Rate limiting on auth endpoints (login/signup brute-force defense)

WHAT WAS FOUND: loginAction/signupAction accepted unlimited attempts;
  scrypt made online guessing slow but not free; OAuth callback token
  exchange was also unbounded. The PL-007 limiter was generic and ready
  to reuse — only auth-specific wiring was missing.

WHAT WAS CHANGED: New src/lib/security/request-key.ts
  (clientIpFromHeaders — x-forwarded-for first hop, x-real-ip fallback,
  "local" for direct access; retryMinutes). authRateLimit() guard in
  src/lib/auth/actions.ts: login keyed per-email (5/15min, NAT-safe)
  plus per-IP (30/15min); signup per-IP (5/hour). Google OAuth callback
  limited 10/15min per IP, fail-closed → /login?error=google_rate:<m>
  with a friendly banner (new resolveAuthError parser on the login page).

FILES/MODULES AFFECTED: src/lib/auth/actions.ts,
  src/app/auth/google/callback/route.ts, src/app/login/page.tsx,
  src/lib/security/request-key.ts (new), tests/request-key.test.ts (new),
  scripts/tmp-auth-throttle.mjs (temporary, removed).

WHY THE CHANGE WAS MADE: Online brute force against login (and abuse of
  the callback's outbound calls) had no cost ceiling. Limits are
  deliberately generous because the user accesses via a shared LAN IP.

TESTS PERFORMED: 6 new unit tests (37 total, all pass) covering XFF
  parsing, fallbacks, NAT keying and retry-minute rounding. Live browser
  hammer test through the real login form: attempts 1-5 → normal auth
  error; attempt 6+ → "Too many sign-in attempts … 15 minute(s)";
  different email on same IP → unaffected; zero console errors. tsc;
  build; smoke 14/14.

VERIFICATION RESULT: all green; live throttle behavior matches design
  exactly (server-side debug line confirmed counts climb 1→5 then block).

REGRESSION CHECK: full gates re-run after removing debug logging —
  tsc clean, 37/37 tests, build OK, smoke 14/14.

NEW ISSUES DISCOVERED: the live test initially LOOKED like the limiter
  was broken; instrumentation proved the app was fine — the harness was
  calling requestSubmit() while the submit button was disabled mid-
  action, so submissions were silently dropped and the stale alert
  matched. Lesson recorded: anchor UI tests on the pending cycle
  (spinner appear → clear), never on stale DOM text.

NEW SUGGESTIONS CREATED: none (post-audit found no new debt; the
  in-process limiter's multi-instance limitation is already documented
  inside rate-limit.ts and revisited by the Postgres phase PL-009).
FINAL STATUS: COMPLETED
